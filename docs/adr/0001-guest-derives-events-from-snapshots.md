# 访客从快照差异还原比赛事件，联机协议保持不变

比赛画布向界面层报告事件（发球、碰撞、屏障击破、进球、得分、获胜），界面据此更新比分、播放声音并统计数据。本地比赛与房主直接在计算时发出这些事件；访客不计算比赛，改为比较相邻两份比赛快照来还原同样的事件，发球倒计时由访客在看到冰球回到中央时自行计时。访客自己的球拍在本机按与房主相同的移动规则先行移动。

这样做是为了不改动 `src/net/protocol.ts` 和已经部署的 Cloudflare Worker：Worker 用同一份 zod 结构校验并转发快照，未登记的字段会被丢弃，新增字段必须先重新部署 Worker 才能到达访客，而且新旧页面会在同一个房间里相遇。

## Considered Options

- **在快照中加入事件列表和发球计时**：访客的声音和统计会更准确，但需要重新部署 Worker，并处理旧 Worker 丢弃字段的情况。
- **只在本机显示访客球拍的预测位置**（已采用）：手感跟手，代价是访客看到的球拍比房主结算时的位置超前一个往返延迟，击球看起来会略早于接触。另一种做法是完全按快照显示球拍，画面一致但操作延迟明显。

## 碰撞记号

边墙改成会抖的弦之后，访客需要知道每次碰撞发生在哪里、有多重。协议没有这样的字段，于是借用快照里原有的 `effects.shockwaves`：房主把每次碰撞的位置写进 `x`、`y`，力度写进 `r`，`alpha` 在几帧内减到零；访客把新出现、且落在边墙或屏障上的条目当作一次拨弦。`effects.particles` 不再使用，始终为空数组。字段名与含义不再一致，这是为了不重新部署 Worker 付的代价。

## Consequences

- 访客画出的球路由插值后的位置连成，与房主看到的略有出入。
- 联机比赛的获胜分数固定为 7：协议把比分限制在 0 至 7，而且访客无从得知房主的设置。
- 以后若要让访客请求再来一局，或者让双方协商局分，需要扩展协议并重新部署 Worker。
